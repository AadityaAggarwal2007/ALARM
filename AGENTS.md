# Driving Discipline from an AI

The planner is built to be operated by a model, not just by hand. Both surfaces
write through the same engine, so nothing you do in the app and nothing an agent
does can drift apart.

The design goal is blunt: **a term of classes should cost one call, not forty.**

---

## Connect an AI

1. Open **Settings → Agent access**, create a token, copy it (shown once).
2. Point any MCP client at `mcp/server.mjs`.

Claude Code / Claude Desktop — add to your MCP config:

```json
{
  "mcpServers": {
    "discipline": {
      "command": "node",
      "args": ["C:\\Users\\Aaditya Aggarwal\\Desktop\\claude\\ALARM\\mcp\\server.mjs"],
      "env": {
        "DISCIPLINE_URL": "https://alarm.axonagent.online",
        "DISCIPLINE_TOKEN": "disc_..."
      }
    }
  }
}
```

Because it talks to the tunnel rather than to localhost, the machine running the
AI does not have to be the machine running the app. Any client, anywhere.

Without MCP, the same thing over plain HTTP:

```
Authorization: Bearer disc_...
```

## Four tools

| Tool | Use |
| --- | --- |
| `get_schedule` | Everything in one call: date, categories, blocks, rules, goals, inbox. Optional discipline summary. |
| `apply_plan` | All writing. Many intents per call. |
| `get_stats` | Time-use and discipline over a period. |
| `describe_api` | The full op reference, fetched live. |

Four rather than forty on purpose: a small, sharply described surface is
answered correctly far more often than a broad one.

---

## The two rules that matter

**Nothing repeats unless asked.** `schedule` creates one-off blocks. It creates
a repeating rule only when you pass `repeat`. Ad-hoc things stay ad-hoc.

**No edit rewrites a rule by accident.** `update` and `delete` default to the
matched occurrences only. If a selector lands on blocks generated by a rule and
no `scope` was given, the call is **refused and nothing is written**:

```json
{
  "ok": false,
  "needsScope": {
    "question": "26 of the 26 matched block(s) come from a repeating rule (\"Physics\")...",
    "choices": {
      "this":   "Only these occurrences. The rule is untouched.",
      "future": "These and the rule, so every future one inherits.",
      "all":    "Every occurrence, past included."
    }
  }
}
```

The agent is expected to put that question to a human rather than guess. Guessing
means silently changing an alarm weeks from now.

`scope: "future"` on a **subset of a rule's weekdays splits the rule** rather
than corrupting it. Changing Fridays leaves Mondays and Wednesdays exactly as
they were, under their own rule.

## Conventions

- **Wall-clock only.** `"2026-09-07"`, `"16:00"`, `"16:00-18:00"`. Never ISO or
  UTC — models get offsets wrong, and this removes the whole class of error.
- **Names, not ids.** Categories and subcategories are addressed by name and
  created on demand, so there is never a lookup call first.
- **Keys.** An op with a `key` can be re-applied: the same plan sent twice edits
  what it made the first time instead of duplicating it.

## Selectors

How you say "those ones" without fetching anything:

| Field | Meaning |
| --- | --- |
| `key` | Blocks made under this plan key |
| `category` / `sub` | By name |
| `from` / `to` | Date range |
| `weekdays` | `["FRIDAY"]` — "the Friday ones" |
| `nth` | `odd` \| `even` — **"half of them"** |
| `enforced` | Only enforced blocks, or only unenforced |
| `ids` | Explicit escape hatch |

---

## Wake modes

An escalation ladder, quietest first:

| Mode | Behaviour |
| --- | --- |
| `SILENT` | One notification, then nothing. A nudge. |
| `VIBRATE` | Notifications repeat ~1/s, so the phone buzzes continuously. |
| `SIREN` | Repeats, plus a loud alarm while the app is open. |
| `VOICE` | Repeats, plus the block spoken aloud while the app is open. |

## A full term in one call

```json
{
  "ops": [
    { "op": "schedule", "key": "physics", "title": "Physics",
      "category": "Study", "sub": "Physics", "time": "16:00-18:00",
      "repeat": { "weekdays": ["MONDAY","WEDNESDAY","FRIDAY"], "until": "2026-12-15" },
      "note": "Physics - problem sets",
      "enforce": { "mode": "SIREN", "challenge": "math", "difficulty": "medium", "streak": 3 } },

    { "op": "schedule", "key": "ca", "title": "CA class",
      "category": "Study", "sub": "CA", "time": "19:00-21:00",
      "repeat": { "weekdays": ["TUESDAY","THURSDAY"], "until": "2026-12-15" },
      "enforce": { "mode": "VOICE", "say": "CA class starting", "streak": 1 } },

    { "op": "goal", "title": "Study 12h a week", "scope": { "category": "Study" },
      "metric": "DURATION", "direction": "AT_LEAST", "target": "12h",
      "until": "2026-12-15" }
  ]
}
```

Measured: **44 blocks, 2 subcategories, 2 rules and a goal in one request.** The
old REST surface needed about forty-six, and could not express "until December"
or per-occurrence variation at all.

Add `"dryRun": true` to see the diff first. Every plan is validated in full
before any of it is written, so a bad op late in a plan cannot half-apply.

## Horizon

Rules are materialised **60 days ahead** on a rolling basis and topped up daily,
so `until` may reach far beyond what `get_schedule` returns. Rows have to exist
to be rung, dragged or graded — the discipline record lives on the row.

Deleting one occurrence writes a **tombstone**, so the daily pass does not
resurrect it.
